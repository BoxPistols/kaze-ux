# 運用モデル — 誰が何を決め、AI に何をさせるか

[`DESIGN.md`](../DESIGN.md) が**システムの層**（データ層 / MCP / Skills / Hook）を
定めるのに対し、この文書は**人の役割**を定める。

デザイナー・エンジニア・PdM・AI エージェントが同じルールセットの上で協働する
ために、「誰が決めてよいか」と「AI に何をさせて何をさせないか」を先に固定する。

> 権限が曖昧なままツールだけ配ると、**AI が最も速く動く方向**に設計が流れる。
> 速さは判断の正しさと無関係なので、判断の主体を先に決める。

---

## 1. 役割と権限

| 役割            | 決めてよいこと                                          | 決めてはいけないこと            |
| --------------- | ------------------------------------------------------- | ------------------------------- |
| デザイナー      | トークンの値、部品の props 契約、禁止ルールの追加、意匠 | 実装技術の選定                  |
| エンジニア      | 実装技術、検査の作り方、生成物のパイプライン            | トークンの値、部品の props 契約 |
| PdM             | 何を作るか、優先順位、スコープ外の宣言                  | トークン・ルール・実装技術      |
| AI エージェント | **何も決めない。** 決まっているものを引いて適用する     | すべて                          |

**AI が決めないことが要点。** AI はトークンを発明しないし、ルールを緩めない。
「引く先が無いから作った」は許されるが、その場合は**なぜ引く先が無かったかを
記録する**（実例: kaze-ec の `ImageGallery` は `search('image')` で DS に
該当部品が無いことを確認してから作り、その旨をカタログに明記している）。

---

## 2. 変えたいときにどこを触るか

**単一ソースは 1 つずつしかない。** 生成物を直接編集すると、次の再生成で消える。

| 変えたいもの         | 触る場所（単一ソース）                           | 再生成                 | 生成物（直接編集しない）    |
| -------------------- | ------------------------------------------------ | ---------------------- | --------------------------- |
| 色・余白・文字・角丸 | `src/themes/`                                    | `pnpm export-tokens`   | `design-tokens/tokens.json` |
| 禁止ルール           | `scripts/lib/ds-rules.mjs`                       | `pnpm export-rules`    | `foundations/prohibited.md` |
| 部品の仕様           | story + `metadata/curated.json`                  | `pnpm export-metadata` | `metadata/components.json`  |
| 使い方の手順         | `skills/`（配布用）/ `.claude/skills/`（内部用） | —                      | —                           |

ルールを 1 つ足すと、`ds-rules.mjs` → `export-rules` → `prohibited.md` →
MCP `check_rule` → Plugin Hook → 消費側リポジトリ、まで自動で届く。
**同じ知識を 2 箇所に書いた時点で設計違反。**

## 3. デザイナーの動線（エンジニアを待たない）

デザイナーが**コマンドを打たずに**完結できる範囲を明示する。
ここが狭いと「結局エンジニアに頼む」に戻り、AI ネイティブにならない。

### 3.1 何ができるか

| やりたいこと               | 打つもの                                   | 前提     |
| -------------------------- | ------------------------------------------ | -------- |
| 今の色・余白を知りたい     | 「primary の色は？」と聞く                 | kaze MCP |
| 部品の props を知りたい    | 「Chip にどんな props がある？」           | kaze MCP |
| この画面が DS 準拠か見たい | `/kaze-design:kaze-ds-review`              | Plugin   |
| UI を作らせたい            | 普通に依頼する（Skill と Hook が裏で効く） | Plugin   |

いずれも `pnpm` も `node` も要らない。**Claude Code に日本語で聞くだけ。**

### 3.2 導入（1 回だけ、2 コマンド）

```
/plugin marketplace add BoxPistols/kaze-ux
/plugin install kaze-design@kaze-ux
```

詳細は [`using-from-other-repos.md`](guides/using-from-other-repos.md)。

### 3.3 できないこと（エンジニアに渡す）

- トークンの**値そのもの**の変更（`src/themes/` を編集して再生成が要る）
- 新しい機械検査の追加
- 生成物パイプラインの変更

**「値を変えたい」はデザイナーの決定事項だが、反映作業はエンジニア**という
分け方にしている。決定と作業を分けないと、権限か再現性のどちらかが壊れる。

## 4. AI に何をさせて、何をさせないか

### させること

| させること                                   | 根拠                                         |
| -------------------------------------------- | -------------------------------------------- |
| 仕様を引く（`get_token` / `get_component`）  | 記憶で補完させない。値は常にデータ層が正     |
| 引いた仕様どおりに実装する                   | 再生成できることが DS の価値                 |
| 自分の書いたコードを検査する（`check_rule`） | 書いた本人が最初の検査者                     |
| 引く先が無いことを確認する（`search`）       | 「無いから作った」と「知らずに作った」は別物 |

### させないこと

| させないこと                           | 起きること                                       |
| -------------------------------------- | ------------------------------------------------ |
| トークンの値を発明する                 | データ層と食い違い、検査をすり抜ける経路ができる |
| ルールを緩める提案                     | 守れないルールが残り、検査が形骸化する           |
| 「たぶんこうだと思います」で仕様を語る | 推測が実測として扱われる                         |
| 検査を無効化して先に進む               | 検査が止めた意味が消える                         |

### 判断に迷ったとき

**引く → 無ければ聞く → それでも無ければ作って記録する。** この順序。
いきなり作るのが一番まずい（記録が残らないので、後から誰も理由を辿れない）。

---

## 5. 検査の責任分担

検査は 3 層あり、**それぞれ止めるタイミングが違う**。

| 層                             | いつ止まるか              | 誰のためか                       |
| ------------------------------ | ------------------------- | -------------------------------- |
| Hook（PostToolUse）            | AI がファイルを書いた直後 | AI 自身。その場で自己修正させる  |
| ローカル検査（`pnpm check:*`） | push 前                   | 書いた人。CI を待たない          |
| CI                             | PR ごと                   | レビュアー。人手の見落としを拾う |

**Hook で止まるものを CI まで持ち越さない。** 手戻りが大きくなるだけで、
検出できる違反の種類は同じ。

## 6. 現場に定着させる 3 段

導入しただけでは使われない。実際に効いた順に挙げる。

| 段  | やること                         | なぜ効くか                                 |
| --- | -------------------------------- | ------------------------------------------ |
| 1   | 消費側の `CLAUDE.md` に 1 行足す | 参照が「習慣」ではなく「既定」になる       |
| 2   | Hook を入れる                    | 忘れても止まる。人の注意力に依存しない     |
| 3   | 検出→修正の履歴を残す            | 「動いている検査」であることを後から示せる |

1 の 1 行:

```markdown
UI の実装・変更時は kaze MCP（get_token / get_component / check_rule）を参照すること
```

3 について。**一度も何も検出したことがない検査は、動いている証拠にならない。**
検出器を作ったら意図的に壊して、検出することを確かめ、その履歴を残す
（実例は [kaze-ec の効果測定レポート](https://github.com/BoxPistols/kaze-ec/blob/main/docs/design-md-report.md)）。

## 7. この体制で守れないもの

**書いておかないと、守れているつもりになる。**

| 守れないもの             | なぜ                                                                     |
| ------------------------ | ------------------------------------------------------------------------ |
| 意匠の質                 | トークン準拠の簡素なデザインは作れてしまう。検査は「一致」しか見ない     |
| 何を宣言すべきかの判断   | 宣言漏れは検出できるが、宣言する対象は人が決める                         |
| ドキュメントの主張の真偽 | 「〜していない」と書いても、検査に接続するまで守られない                 |
| ドメイン知識             | 「フリマなら複数写真が要る」は DS からは出てこない                       |
| 検査の免除リストの正当性 | 免除したものについて検査は何も言わない。0 件は「宣言した範囲で違反なし」 |

いずれも**人が見るしかない**。機械検査は人のレビューを置き換えない。
**レビューする対象を減らす**だけで、レビュー自体は残る。

### 免除リストについて補足

最後の 1 行は kaze-ec で実際に踏んだ。`Table` が「宣言しなくてよい部品」に
入っており、DS に仕様が実在するのに検査対象外になっていた。外した途端に
既存画面の無申告が 1 件出てきた。

**検査の穴は検査では見つからず、新しい利用者が踏んで初めて出る。**
このときも、見つけたのは新しい画面を作る過程で「なぜ Table は宣言しなくて
いいのか」と引っかかった側だった。消費側のリポジトリが無ければ出ていない。

対策は、免除リスト自体を検査すること。kaze-ec の `checkAllowlist` は
allowlist の各エントリに `get_component` を投げ、実在するものが免除されて
いたら検査を落とす。**免除を書くたびに、その正当性が検査される。**

### 同じことが MCP の `check_rule` でも起きていた

`scripts/lib/ds-rules.mjs` は禁止パターンの単一ソースだが、
`mcp/src/tools/check-rule.ts` が**独自のパターン一覧を持つ第 2 の正**に
なっていた。結果:

- `AI04`（角丸と片側だけの太いボーダー）は ds-rules に検出器があるのに
  MCP からは検出されず、**消費側にルールが届いていなかった**
- `A01` は ds-rules では「24x24 未満の操作対象」だが、check-rule.ts は
  「IconButton の aria-label 欠落」を検査していた。説明文は prohibited.md
  から引くので、**違反理由が実際の検出内容と食い違って表示されていた**

後者は検出漏れより悪い。読んだ AI は書かれた理由を信じて直そうとする。

直したこと。

| 変えたもの           | 内容                                                                                           |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| `check-rule.ts`      | 検出器を `ds-rules.mjs` から読む（第 2 の正を削除）                                            |
| `sync-mcp-data.mjs`  | `ds-rules.mjs` を npm 配布物に同梱。説明文だけでは検査できない                                 |
| 検出器が無いとき     | 「違反なし」ではなく「**検査していない**」と返す                                               |
| 応答                 | 検査したルール ID と、検査していないルール ID を必ず併記する                                   |
| `check-rule.test.ts` | 全検出器に既知の違反サンプルと非違反サンプルを持たせ、**サンプルの無い検出器を足したら落ちる** |

直した直後、消費側 (kaze-ec) で本物の違反が 1 件出た（`fontSize: 11`）。
**ルールは前から在ったが、届いていなかっただけ。**
