# 分かっている穴と不整合

このデザインシステムで**現在守れていないこと**と、**過去に壊れていて直したこと**を
隠さず並べる。

書く理由は 2 つ。

1. **穴を知らずに使うと、0 件の検査結果を「準拠している」と読む。**
   実際には「検査していない範囲がある」だけのことが多い
2. **同じ壊れ方が繰り返される。** 型に名前を付けておくと、次に気づける

数字は [`coverage.md`](coverage.md)（生成物）を見ること。ここには
数字に現れない問題を書く。

---

## 1. 今も残っている穴

### 1.1 A05 の判定は、静的に分かる範囲しか見ていない

`A05`（アイコンだけのボタンに読み上げ名が無い）は**取りこぼす方向**に
倒してある。次の形は違反にしない。

| 形                              | 理由                                                                      |
| ------------------------------- | ------------------------------------------------------------------------- |
| `{...props}` を展開している     | 名前が渡ってくるか静的に分からない                                        |
| `<Tooltip title={expr}>` で包む | title が文字列なら MUI が aria-label にするが、値は実行時にしか分からない |
| `IconButton` 以外の自作ボタン   | タグ名で引いているため                                                    |

**誤検出のほうが害が大きい**という判断。検査が信用されなくなると、
次からは中身を見ずに素通りさせるようになる。

取りこぼす範囲は実描画の a11y 検査（`pnpm check:a11y`）で拾う。

### 1.2 これは解決済み（記録として残す）

以前ここには「aria-label / alt を今どこも見ていない」と書いていた。
`A05` / `A06` を正式なルールとして追加し、検出器を書いて解消した。

追加した直後、**本体で 4 件の本物の違反が出た**（コードブロックのコピー
ボタン 2 件、チャットの送信ボタン、サイドバーの開閉トグル）。いずれも
アイコンだけのボタンで、読み上げでは「ボタン」としか言われない状態だった。

### 1.3 何も止めないルールが 4 件ある

`K01`（ハードコード色値）/ `A04`（色だけで状態を伝える）/
`AI01`（カード上部の意味の無いカラーバー）/ `AI02`（過度なグラデーション）。

**書いてあるだけで、破っても誰も気づかない。**

`K01` は消費側（kaze-ec）では宣言済みトークンとの突き合わせで検査している
（`tools/drift/check-drift.mjs`）が、**kaze-ux 本体では検査していない**。
供給側のほうが緩い、という逆転が起きている。

`AI01` は検出器を書いていない。カード上端の細い装飾バーを機械判定しようと
すると、正当なレイアウトを巻き込む。`AI04` が sx と className の両方で
同じ形を捕まえるので実害は小さいが、**「AI01 は検査されている」とは言えない**。

### 1.4 部品メタデータの充足率が低い項目がある

`accessibility` 25.5%、`sizes` 30.9%、`variants` 32.7%、`description` 54.5%。

これは「AI が引ける情報」の欠落なので、**引けなかった AI は推測で埋める**。
数字は [`coverage.md`](coverage.md) が測っている。

`sample` は 7.3% → 41.8%、`prohibited` は 3.6% → 20% まで埋めた。やり方が
2 つに分かれる。

**`sample` は型検査に接続した。** 手で書いた文字列を検査せずに配るのは、
守られていないルールを `prohibited.md` に載せるのと同じ「嘘の仕様」になる。
`pnpm check:samples` が sample を本物の tsx に組み立てて `tsc` に通す。
書いた時点で 11 件が落ちた（自由変数が残っていて、読んだ側が補う必要が
あった）。`<Snackbar open={open}>` は `window.open` を拾って型エラーになり、
sample 自体が誤りだったことも分かった。

**`prohibited` は導出にした。** 「アプリからこの MUI 部品を直接 import
しない」は `scripts/ds-equivalents.mjs` が既に持っている。手で書くと
2 つの正になり、DS に部品を足したとき片方だけ古くなる。ESLint と
DS 準拠率の計測も同じ表を見ているので、ここも同じ表から出す。

導出の条件を間違えて、最初は **DS 部品側にも「DS を使え」と付いた**
（「IconButton を使うな、DS の IconButton を使え」という循環）。
DS 実体と MUI 実体が同名なので、名前だけでは判別できない。
`import` が `@mui/material` のエントリに限定して解消した。

残る 4 項目は導出元が無いので、埋めるなら人が書くことになる。

### 1.5 `check-react-fc.sh` は検体と実使用を区別できない

`.ts` / `.tsx` を grep するだけなので、**テストの「既知の違反サンプル」を
違反として数える**。実際 `mcp/src/tools/check-rule.test.ts` を書いたときに
pre-commit が止まった。

`ds-rules.mjs` は `stripLiteralsAndComments` でこれを解いているが、
シェル側には入っていない。今は検体の文字列を分割して回避している。

### 1.6 `T01`（12px 未満）の検出器は「書かれた値」しか見ない

`fontSize: 11` や `text-[11px]` は捕まえるが、計算結果や CSS 変数経由の値は
見ない。実描画を測る `check:typo` が本命で、**こちらは MCP 経由で
コード片しか渡されない場合の保険**。

### 1.7 他のデザインシステムから使うと、検査が無い

`DS_ROOT` で別のデザインシステムを指すと、そこに `scripts/lib/ds-rules.mjs`
は無い。検出器が読めないので `check_rule` は
「**検査していません**（違反なしではありません）」と返す。

これは設計として正しい（kaze のルールで他所を採点しない）が、
**他 DS の利用者には実質 `get_token` / `get_component` / `search` だけ**に
なる、という意味でもある。

## 2. 壊れていて直したもの

**直したものも消さない。**同じ型が再発するため。

### 2.1 配布の入口がスキーマ違反で壊れていた

`.claude-plugin/marketplace.json` の `owner` が文字列だったため
`claude plugin validate` が落ち、**プラグイン導線そのものが機能していなかった**。

気づいたのは消費側（kaze-ec）を作って実際に
`/plugin marketplace add` を叩いたとき。**供給側からは見えなかった。**

### 2.2 MCP が、同じ ID で別のルールを検査していた

`mcp/src/tools/check-rule.ts` が検出パターンを自前で持ち、
`scripts/lib/ds-rules.mjs` と**2 つの正**になっていた。

| ID  | ルールブックの内容        | 実際に検査していたもの        |
| --- | ------------------------- | ----------------------------- |
| A01 | 24x24 未満の操作対象      | IconButton の aria-label 欠落 |
| A04 | 色だけで状態を伝える      | img の alt 欠落               |
| T01 | 12px 未満のフォントサイズ | px 指定の fontSize すべて     |
| K02 | 面の色を文字色に流用      | `text-black` / `text-white`   |
| K03 | `--color-*` の手打ち      | `bg-gray-*`                   |

説明文は `prohibited.md` から引くので、**違反理由が実際の検出内容と
食い違って表示されていた**。検出漏れより悪い。読んだ AI は書かれた理由を
信じて直そうとするので、直らないうえ理由も分からない。

さらに `AI04`（角丸と片側だけの太いボーダー）は ds-rules に検出器が
あるのに check-rule.ts に無く、**MCP からは検出されなかった**。
消費側でこのパターンを書いても止まらなかった。

直した内容は [`operating-model.md`](operating-model.md) の
「同じことが MCP の `check_rule` でも起きていた」を参照。
繋いだ直後、消費側で本物の違反が 1 件出た（`fontSize: 11`）。
**ルールは前から在ったが、届いていなかっただけ。**

### 2.3 検出器があるのに「何も止めない」と表示していた

`C02` / `C07` / `A03` / `AI04` は `enforcedBy: null` のままだった。
実際は `check:rules` が CI で走り、違反があれば exit 1 する。
つまり**止まる**。

その結果、カバレッジ表が「何も止めないルール 38.1%」と報告していた
（正しくは 19.0%）。**自分の状態を実態より悪く申告していた。**

再発防止として `ds-coverage.mjs` が、検出器があるのに `enforcedBy` が
空のルールを見つけたら exit 1 する。

### 2.4 DESIGN.md の主張が偽になっていた

「トークンやコンポーネント仕様もこのリポジトリには一切バンドルしていない」と
書いていたが、消費側の `theme.ts` に hex 値が存在し、しかも検査対象外だった。

**「〜していない」と書いた時点では真でも、実装が進むと静かに偽になる。**
主張を検査に接続するまで守られない。

### 2.5 新しい検出器が、実装済みの 17 箇所を誤検出した

`A05` を足した直後、17 件の違反が出た。**うち 13 件は誤検出だった。**

| 誤検出の形                                   | 実際は                                     | 気づき方                                      |
| -------------------------------------------- | ------------------------------------------ | --------------------------------------------- |
| `<Tooltip title='編集'>` で包んだ IconButton | MUI が子に `aria-label` を付ける           | `Tooltip.js` の実装を読んだ                   |
| DS の `IconButton tooltip='メモ追加'`        | `accessibleLabel = ariaLabel \|\| tooltip` | `iconButton.tsx` を読んだ                     |
| JSDoc の `@example` に書いた使用例           | コードではない                             | `stripLiteralsAndComments` を通していなかった |

**検出器は、既知の違反と既知の正解の両方で確かめてから信じる。**
違反サンプルだけ用意して「検出できた」で止めていたら、13 件の誤検出を
そのまま CI に入れていた。

`check-rule.test.ts` に、読み上げ名がある形 5 通りを「検出しない」側の
テストとして固定してある。

### 2.6 正しい方針をコメントに書くと違反になる検出器があった

上の型を別プロジェクト（adlumetra）に共有したところ、向こうの走査検査でも
**正解サンプル 6 件が全部落ちた**。とくに効いたのが
「業界平均は使わない」という**正しい方針をコメントに書いた瞬間に落ちる**
ケース。原因は、検出したいのが画面やスキーマに出る文字列なのに、
コメントまで走査していたこと。

**同じ状態がこちらにもあった。** `T01` / `AI03` / `AI04` の 3 つが
コメントを落としていなかった。実測すると 8 件中 3 件で誤検出。

```
誤検出 [T01]  /** fontSize: 11 のような指定は禁止 */
誤検出 [T01]  const msg = "fontSize: 10 は違反です"
誤検出 [AI04] const doc = `<Card sx={{ borderRadius: 2, borderLeft: 4 }} />`
```

直し方に一段ある。**`stripLiteralsAndComments` を当ててはいけない。**
文字列の中身まで `''` になるので `fontSize: '11px'` が見えなくなる。
この repo の font-size / border 宣言 812 件のうち **347 件（43%）が
引用符付き**なので、それを失うほうが害が大きい。

コメントだけを落とす `stripComments` を足した。URL の `//` をコメントと
誤認しないよう、文字列の中かどうかを追跡している
（「直前がコロンなら除外」のような手当てでは、文字列中の他の `//` を取り逃す）。

直した後: 誤検出 0/8、検出漏れ 0/10。両側の検体をテストに固定してある。

### 2.7 MCP が、起動時のデータを返し続けていた

`metadata/components.json` に sample を 19 件足した直後、消費側から
`get_component('statusTag')` を呼んだら **sample の無い古い応答**が返った。

MCP サーバはトークン・部品仕様・禁止ルールをプロセス生存中ずっと
メモリに持っていた。サーバはエディタが起動している間ずっと動いているので、
**デザインシステム側が更新しても、消費側は再起動するまで古い値を受け取る**。

気づきにくいのは、**古い値も正しい形をしている**こと。sample が無い応答は
「まだ sample を書いていない部品なのだろう」と読める。値が壊れていれば
気づくが、古いだけだと気づかない。

これは MCP が単一ソースの「古い写し」になる状態で、このリポジトリが
検出対象にしているもの（第 2 の正）そのもの。mtime を見て、変わっていれば
読み直すようにした。サーバを起動したまま書き換え→反映→書き戻し→反映を
実測して確認し、テストにも固定してある。

### 2.8 検査の免除リストが沈黙していた

消費側のドリフト検査で `Table` が「宣言しなくてよい部品」の免除リストに
入っていた。`get_component('table')` は実在するのに検査対象外。
外した途端、既存画面の無申告が 1 件出た。

**0 件は「準拠している」ではなく「宣言した範囲で違反がない」。**

## 3. 繰り返し出てくる型

上の 8 件は別々の事故に見えるが、4 つの型に収まる。

| 型                                 | 内容                                                 | 見分け方                                 | 該当            |
| ---------------------------------- | ---------------------------------------------------- | ---------------------------------------- | --------------- |
| **第 2 の正**                      | 同じ知識が 2 箇所にあり、片方だけ更新される          | 「同じことを書いた場所」を数える         | 2.2 / 2.7       |
| **沈黙する検査**                   | 検査していない範囲について何も言わない               | 0 件のとき、何を検査したか出るか         | 2.8             |
| **接続されていない主張**           | ドキュメントに書いたことを検査していない             | 「〜していない」と書いた箇所を検査に繋ぐ | 2.1 / 2.3 / 2.4 |
| **片側でしか確かめていない検出器** | 違反サンプルだけで作り、正解サンプルを用意していない | 「検出しない」側のテストがあるか         | 2.5 / 2.6       |

最後の 1 つは、他の 3 つと向きが逆になる。**検出しなさすぎ**ではなく
**検出しすぎ**で、放置すると検査そのものが信用されなくなり、
以後は中身を見ずに素通りさせるようになる。

そして共通するのは、**検査の穴は検査では見つからない**こと。
2.1 / 2.2 / 2.7 / 2.8 はいずれも、**消費側から実際に呼んだ過程で**
出てきた。供給側の中だけを見ていて見つかったものは 1 件も無い。
2.5 は**新しい検出器を実コードに当てて**、2.6 は**別プロジェクトから
共有された型を自分に当てて**出てきた。いずれも「外から来たもの」が
きっかけになっている。
