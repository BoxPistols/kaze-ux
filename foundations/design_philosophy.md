# Kaze Design System — 設計思想

## Core Belief

> 決めたことが、守られている。

「規約を決めた」と「規約が守られている」は別物で、その差は毎回**測ってはじめて
分かった**。このデザインシステムは、決めごとを人にも AI にも同じように読める形で
配り、守られていることを実測で確かめる。

## 3 つの原則

### 1. 決めごとは、守らせ方まで含めて決める

ルールには**何が違反を止めるのか**を必ず添える。止める仕組みが無いものは
「なし」と明示する。書いてあるだけのルールは、読んだ人にも AI にも嘘の仕様になる。

実測した例: `export default` 禁止は 33 箇所で破られ、止めるものは何も無かった。

### 2. 仕様は、人と AI が同じものを読む

トークン・部品の仕様・禁止パターンを、機械可読な単一ソースから生成して配る。
手で書いた一覧は必ず実装から遅れ、**遅れてもエラーは出ない**。

説明を読んだ AI は従い、コードを読んだ AI は真似る。両者が食い違うと、
どちらが正しいか判断できない。

### 3. 見た目は縛らない。原則だけを縛る

色・書体・余白の選び方は各プロダクトのもの。共通で保証するのは土台だけ。

- 本文コントラスト 4.5:1（実際に敷かれる面で測る）
- 操作対象 24×24 以上（WCAG 2.2 SC 2.5.8）
- フォントは 12px 以上、ウェイトは 400 / 700
- 色はトークン参照。ハードコードしない

## 運用の作法

**生成物にする。** トークン・部品仕様・禁止パターンの文書はすべて生成物で、
CI が「再生成して差分が出ないこと」を検査する。手で編集しない。

**壊して確かめる。** 検査は導入時に一度壊して赤くなることを確認してから信用する。
緑を見ただけでは、機能しているのか何も見ていないのか区別できない。

**黙って減らさない。** 検査の対象外にしたものは、理由と件数を必ず出力する。

**測れないものは測れないと書く。** 意匠の良し悪しなど機械判定に向かないものに
検出器を付けない。付けると誤検出のほうが多くなる。

## 面ごとに前景色を持つ

色の扱いだけは他と違う癖がある。**塗り面と前景で別のトークンを持つ。**

| スロット       | どこに使うか                                  |
| -------------- | --------------------------------------------- |
| `main`         | 塗り面                                        |
| `contrastText` | `main` の面に乗る文字（実測で決定）           |
| `onLight`      | `light` の面に乗る文字                        |
| `textContrast` | 素の背景と `lighter` の面に乗る文字・アイコン |

`primary.main` をそのまま文字色にすると、明るいセマンティック色は白地で
2.6:1 程度しか出ない。**面が違えば必要な前景色も違う**ので、面ごとに持つ。

## フレームワークとの関係

トークン・色の計算・タイポグラフィの層は **UI ライブラリに依存しない**。
CI が依存グラフを辿って保証している（`scripts/ds-core.mjs`）。

MUI を使わないプロダクトは `design-tokens/kaze-tokens.css` を読み込むだけで
同じ色に乗れる。部品は現状 MUI 製が多く、そこは移植が要る。

## ブランド

- **Primary**: `#0057B8` — 白文字が 6.87:1 出る。ロゴとテーマが `BRAND_BLUE` を
  単一ソースとして共有する
- **Font**: Inter + Noto Sans JP。見出しも本文も同じグロテスクで、階層は太さで作る
- **Grid**: 4px 基準
- **Border Radius**: xs(4) / sm(6) / md(8) / lg(10) / xl(12) / 2xl(16)

## 実証

SaaS Dashboard / KazeEats / KazeLogistics の 3 プロダクトで運用している。
どれも DS 採用率 100%（`pnpm ds:adoption`）。
